# Verified authentication migration preparation (#81)

Customers retain PIN/passkey; administrators retain password/passkey. This preparation release preserves legacy authenticators until the separately reviewed retirement migration. It never deletes legacy secrets or establishes production readiness from a session, code presence or test result.

## Evidence and support

Run `npm run auth:migration:readiness` with the API database/pepper available through normal protected operations. It opens a repeatable-read **READ ONLY** transaction, never initializes the schema, and prints only counts, blocker codes and an opaque inventory digest. `--state-file PATH` supports protected offline snapshots; `--require-ready` exits2 for unresolved blockers. Do not attach snapshots, secrets or per-account inventories to GitHub.

Configured valid Argon2 hashes and structurally usable public keys are counted separately from credentials that actually passed fresh verification. Each verified marker binds the exact PIN/password hash or passkey public key. A credential change/removal, staff deactivation or role/inventory change invalidates the relevant review. Customers with no retained credential block cutover; every authenticator account (including suspended accounts) needs a verified replacement; every active administrator needs verified password/passkey and at least one active owner. A PINless passkey account can enroll its PIN with a signed assertion requiring user verification.

Customers open Account → authenticator controls → migration preparation. Existing PIN/passkey users verify that method. PINless authenticator users verify their current TOTP or unused authenticator recovery code, choose matching four-digit PINs, then re-enter the new PIN in a separate confirmation step. The same-session ten-minute intent contains an Argon2 hash, never the plaintext PIN. Cancellation, expiry, factor changes and five failures prevent completion. Only confirmation saves the PIN and revokes other portal sessions. Existing TOTP remains available. The browser also exercises a subsequent real PIN login.

Unsupported/cancelled passkeys fall back to the existing PIN/current factor. Lost credentials use the existing owner-audited support PIN recovery: fresh administrator password, recorded case/reason, in-person or existing verified-channel identity review, short-lived single-use support token and PIN-reset confirmation. No SMS is assumed. A configured field is not proof that this recovery route was piloted. Legacy destructive reset-authenticator now returns410 instead of deleting all passkeys and legacy factors.

Owner preparation UI shows aggregate readiness and verifies the owner's password/passkey. After actual staging recovery and authentication pilots, record their evidence reference and the compatible40-character rollback SHA in the guided owner readiness report, or with POST `/api/admin/authentication-migration/review`, `expectedDigest` from the freshly reviewed owner status report, fresh owner proof, `supportRecoveryVerified:true` and `authenticationPilotVerified:true`. Passkey review options bind the exact digest, rollback SHA and reference. Review expires after30days and becomes invalid if inventory changes. These explicit attestations record external review; they do not substitute for doing the pilots. No route in preparation activates retirement.

## Sensitive-action policy inventory

- Customer phone/email/PIN and independent backup-code changes: existing fresh PIN or purpose/target/session-bound required-UV passkey; legacy additional TOTP applies only before retirement. Keep CSRF/throttle/attempt limits. Email/contact verification and support tokens retain their independent meanings.
- Customer/admin passkey add/remove and admin staff changes require fresh PIN/password or an existing user-verified passkey during preparation too. Enrollment challenges bind the session and exact credential versions; removing a key requires a verified remaining supported method. This prevents a stolen session from creating its own replacement and manufacturing readiness. Legacy initial authenticator enrollment also requires fresh owner verification; retained legacy login remains available.
- Main-device designation/replacement, disconnect and Forget: existing PIN/required-UV proof plus independent current controller/router authority; #82 removes only the extra legacy factor, preserving exact target/generation semantics. Shared device files belong to #78-80 and are integrated through reviewed Git changes.
- Admin owner/support recovery: current owner password and reviewed identity/case now; #82 adds the common password/UV proof helper and retires extra TOTP. Routine scoped voucher/read operations retain their current role/session/CSRF policy; payment/provider/router safety remains independent.
- Admin proof helper binds active user/current role/current session, purpose, exact target and credential versions, consumes five-minute challenges and enforces required UV/signature/RP/origin/counter. Five failures lock15minutes. PIN cannot substitute for an admin password. Registration/sensitive challenges cannot be accepted as login challenges.

Wi-Fi access/pairing codes never authorize account migration. Voucher setup now rejects accounts with any established credential; already-issued setup intents cannot overwrite a newly established factor. Exact CSRF/edge maps register migration and proof routes; migration endpoints also enforce exact origin/session CSRF inside the buffered transaction.

## Persistence and compatibility

Proof state lives in existing private customer/admin JSON payloads; owner review and later retirement marker live under the existing persisted `zone` setting. API projections omit private markers/hashes. A dedicated PostgreSQL regression verifies reopen/rollback behavior when `TEST_DATABASE_URL` is supplied by CI. No schema migration or new unregistered collection is required.

This revision understands `zone.authenticatorRetirement.version:1`: old customer/admin authenticator entry points and enrollment/recovery return410 `AUTHENTICATOR_RETIRED`, and stale environment/profile flags cannot reactivate legacy authentication. Production startup no longer requires obsolete MFA environment variables. Keep their current values through preparation; remove only after retirement API compatibility is deployed. Marker awareness alone does not make this first preparation revision a sufficient post-cutover rollback target. The #82 compatibility runtime must first deploy with the complete fresh supported-proof policy while retirement remains inactive. Record and rehearse that exact runtime SHA as the compatible preparation rollback target before any CLI cutover. Rollback preserves current database state and never restores deleted secrets or rewinds new account activity.
