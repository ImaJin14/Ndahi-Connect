# Verified transactional email (#141)

Email stays optional. A newly supplied signup address requires mailbox ownership confirmation before trusted account recovery or document delivery. Existing linked legacy addresses keep their existing compatibility contract. Checkout payer/contact email is a separate payment field and cannot replace a linked account email. PIN/passkey proof, session/address binding, ten-minute expiry, five incorrect-code attempts, request throttles and session rotation remain enforced by the existing Account email routes. The unified security work (#129) is already on main. This change uses the existing profile email form; #130's combined profile editor remains a separate issue.

Account → Notification settings has one persisted transactional-email switch for welcome, receipts, voucher documents and activation notices. Existing security-email consent remains separate. Verification is an explicit mailbox-confirmation request, independent of notification consent. Mandatory security/action inbox history remains available. Email consent never changes purchase, bundle quota, activation or Wi-Fi authorization.

## Outbox and provider contract

No new provider, queue infrastructure, credentials or database schema is introduced. Existing durable domain rows hold delivery state: `pendingEmail.delivery`, `customer.welcomeEmail`, voucher `emailDelivery`/`activationEmail`, payment `receiptEmail` and `securityAlerts`. Voucher flat delivery status fields remain compatible with existing clients. The thirty-second billing timer runs transactional email independently from payment reconciliation so provider slowness does not delay mailbox verification. Security retains its existing worker timer. Workers commit claims before provider I/O and recheck current ownership/consent after claiming. An already in-flight email cannot be recalled after a user changes consent.

Each event uses a stable provider idempotency identity (verification request, customer welcome, voucher, activation, payment receipt or security-alert ID). Lease tokens fence stale completions; an expired lease can recover after restart. Retries back off at 2/4/8/16/30 minutes and stop at five attempts (eight for security), or 23 hours after the first attempt. Resend [retains idempotency keys for 24 hours](https://resend.com/docs/dashboard/emails/idempotency-keys); the shorter retry window avoids automatically resending after its protection expires. A changed verified recipient after an uncertain attempted send cancels automatic delivery for that event and directs the owner to the portal/support. Sent rows stay sent on webhook/status replay. The old verified mailbox may still receive the specific email-replacement security warning.

Verification codes are regenerated with a domain-separated HMAC from the existing server pepper and random request ID, customer, session and address. Only the existing keyed code hash and metadata are saved; raw codes are not persisted. Current/previous peppers support rotation. Old pending requests without the new outbox are still confirmable using their existing code and expiry; request a new code for retry. Raw provider messages, addresses, credentials, codes and document payloads never enter delivery logs/status. Internal outbox payloads/tokens are omitted from customer response projections.

Welcome, verification, voucher, activation, security and PIN recovery messages share NDAHI styling. Receipts retain the existing branded receipt document/PDF. Voucher emails attach the existing branded voucher PDF, with deterministic issuance metadata so retries reconstruct the same bytes. Voucher codes stay out of subjects and URL parameters. Ordinary account/document links require portal authentication; no new public bearer document link exists. Existing one-use, expiring PIN recovery links keep their current scope. Email provider acceptance never proves inbox arrival or Wi-Fi connectivity.

## Status and verification

Status is `pending`, `sending`, `sent`, `failed`, `needs_email`, `disabled`, or `cancelled` (security also retains `skipped`). Failure status exposes a fixed safe explanation, attempt count and next retry; downloadable documents remain available in the authenticated portal. Automatic retries do not reset exhausted counters. Check verified association and notification preferences before investigating provider configuration; do not blindly replay a delivery after its idempotency window.

Automated coverage includes optional signup and payer/account separation, fresh credential/mailbox proof, wrong account/session, replacement, expiry/replay, lost-response recovery, consent changes, two-worker races, leases, provider timeout/outage, stable templates/PDFs, bounded retries and secret-safe projection. PostgreSQL tests additionally cover rollback with payment/voucher state, independent store instances, committed leases and restart/reopen recovery. Browser journeys run at 320/1280px for replacement, queued/invalid/uncertain replies, preferences, retry and reload; existing signup-without-email and passkey/profile journeys remain in CI.

Local checks and exact revision CI results are recorded in the PR. Release remains held for explicit user confirmation after #137/PR153. Not merged or deployed. No production/provider credentials are changed and no real email, charge or router command is performed for acceptance. Configured-domain send/receipt/bounce webhook acceptance, spam placement, inbox arrival and physical device delivery remain unverified operator work after approval; offline fixture success does not establish those outcomes.
