# Customer authenticator sign-in

An authenticator is an optional sign-in method. Enabling it does not require
PIN plus authenticator at every login: customers can still choose their PIN,
an enrolled passkey, or an authenticator code. This is the current product policy.

## Set up an authenticator

1. Sign in and open **Account → PIN, authenticator & passkeys → Enable authenticator 2FA**.
2. In a time-based authenticator app, add an account. Scan the displayed QR code
   from another device. On the same phone, use **Copy setup key**, enter it manually
   in the app, and select **Time based**. The label is NDAHI Connect and the account
   phone number. Codes have six digits and change every 30 seconds.
3. Return to the portal and enter the app's current code, then choose **Confirm 2FA**.
   Setup is enabled only after a valid code is confirmed. The account page then
   shows it as enabled; the setup key and QR disappear.
4. Save authenticator recovery codes from the account page if desired. Each code
   works once. PIN, account backup-code recovery and existing support recovery
   remain separate options.

Keep setup keys and QR images private: either can recreate the authenticator.
QR images are generated by the API itself; no external QR service receives the
secret. Enrollment responses are uncached, and the portal does not save the key
in browser storage or a URL. Automatic application updates wait during setup.

## Expiry, cancellation and retry

Setup lasts ten minutes and must be confirmed in the same signed-in browser
session that started it. Starting again invalidates earlier pending keys for that
account. A setup cannot overwrite an already-enabled authenticator.

**Cancel setup** removes that browser's pending setup without enabling anything.
Five incorrect confirmation codes invalidate a setup; restart with the new QR/key.
There are at most five setup starts per account in fifteen minutes, in addition
to the existing authentication traffic limit. If codes fail, enable automatic
date/time on the phone and use the current code. Expired or replaced setups clear
their displayed key and prompt the customer to start again. Existing enabled
authenticators do not need to be enrolled again after deployment.

## Device linking and sensitive actions

Selecting or replacing the main browser requires fresh PIN or passkey proof.
An authenticator code is optional there; if entered, it is checked. Assisted Wi-Fi
pairing uses the new device's separate five-minute pairing code and main-browser
approval, without an authenticator requirement. Enrolling an authenticator is
not a prerequisite for connecting another device.

Main-device removal and existing sensitive account changes retain their enrolled
authenticator checks. Selecting a new main browser still revokes the previous
controller. See [device management](device-management.md) and
[assisted Wi-Fi pairing](assisted-wifi-pairing.md).

## Validation and rollout

Deploy the API and customer portal together; no database schema change or router
configuration change is needed. Pending setups created before this version must
be restarted because they lack a browser-session binding.

Automated checks cover independent RFC 6238 vectors, enrollment/confirmation and
PIN/authenticator sign-in, customer/session isolation, CSRF, suspension, expiry,
attempt limits, cancellation, stale-key replacement and optional device linking.
The browser checks independently decode the displayed QR pixels and exercise
manual-key copying, retry/cancellation, confirmation, recovery-code sign-in and
a 320px screen. These use synthetic accounts and do not establish a production
rollout or a physical phone scan. After deployment, check setup with a test account
and a real authenticator app, then verify PIN sign-in and Wi-Fi linking without
an authenticator code.
